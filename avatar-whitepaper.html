01 · State of the app

A working world, creator toolkit and connected game economy.

MUZIKAZ World currently combines browser-based 3D exploration, shared server rooms, a visual map builder, persistent member inventories and two connected marketplaces. Its destinations contain distinct games, services and production activities. The new logic connects native object functions, earned stock, manufactured assets, delivery records and eligible sales through the existing account system. This is a source-code snapshot of the available implementation, with further balancing, device testing and operational work still required.

Gameplay, movement and recovery

Implemented

Authoritative room commands calculate supported movement, collision, combat, health, pickups, quests, seats, vehicles and machine actions. Local walking and vehicle prediction respond between snapshots; accepted server state reconciles the view. Swept collision, clear-entry searches, ordered inputs and room-change checks address thin walls, obstructed arrivals, stale held controls and reconnects. These systems support activity-specific rules rather than one universal campaign.

Games, residents and facilities

Implemented

Sports, arcade attractions, fishing, freight, fitness, casino tables, the funhouse, factory work and proving-ground activities have their own runtime rules and rewards. Contextual residents support conversations, local jobs, routines and saved relationships. An authored object must retain the required function data and service context to behave as its map version does.

Native economy and production

Implemented

Catalog pricing, MZK charges, reward receipts, factory asset records, shipment acceptance and eligible listings use server logic. Purchases validate ownership and current funds; repeat request IDs prevent duplicate charges or delivery. Factory item creation records identifiable application assets and provenance. The valuation and production sections explain how those records move into use and sale.

Accounts, Backpack and persistent records

Implemented

The Node service owns account sessions, wallet identity, inventory, ledger history, deeds, maps and shared-room saves. Cookie-authenticated changes require CSRF proof; gameplay session proof is limited to game access. Wallet connection uses a signed challenge. Browser caches and edited files cannot establish paid ownership, and account inventory is not automatically an on-chain token.

Payments, media and headset use

Conditional

Their presence in the app does not establish that every external service or physical headset was tested in this review.

Operations, capacity and remaining work

Further development

The current backend uses serialized JSON stores and a persistent disk under one Node process. Master-state export and controlled restore are implemented. Multiple replicas need a shared transactional store and room-ownership design. Physical-device benchmarks, public-room load tests, economy balancing, moderation and uniform avatar compatibility remain work to measure and improve.

03 · Worlds, districts and land

A shared directory, with distinct places inside it.

The atlas is a navigation system for multiple maps and rooms. Connected destinations share identity, inventory and routing services; entering another destination changes the active room. They are not all simulated as one uninterrupted terrain or one unlimited multiplayer match.

Full world maps

Large procedural layouts, district generators and compatible 3D environments provide the surrounding space. Builder world-size choices extend up to 320 metres for supported procedural presets.

Activity scenes

Fourteen compact sets—including the firing range, vendor street, mazes, arenas and movie studio—can be placed inside a world and moved, rotated and scaled independently.

Rooms & objects

Eight small inlay choices provide floors, rooms and compounds. Buildings, furnishings, machines, characters and other items retain their own placement and gameplay configuration.

Hosted destinations

Published maps and revealed deed entitlements resolve to stable server destinations. Transfers change the owner of an eligible deed while keeping its hosted room and saved content.

Public world

Districts and commons

The original atlas seed lists eight district pins, five public-area plots and seven connecting routes. Those seed figures are not the total number of playable destinations: published builds, repository environments and hosted land extend the directory.

Land entitlement

Ownership and access

A deed is an account entitlement with a hosted location and applicable build or upload permissions. Public exploration, free built-in placement, paid asset ownership and permission to publish or modify a destination are separate decisions.

Destination integrity: a pin or portal points to a server map record. Room access and current ownership are checked by the relevant service. Missing assets, private destinations or an unavailable backend can prevent entry; the roadmap calls for clearer diagnostics and broader destination coverage tests.

05 · The world builder

A world, its scenes and its objects. Independently editable.

The creator dashboard groups tools by task, with category browsing, searchable controls and paged panels on desktop and mobile. Building is a composition workflow: choose the surrounding map, place smaller experiences inside it, then furnish and configure them.

  3. Place assetsTap a destination or drag onto the map
  4. ConfigureTransforms, appearance and interactions

Separate map and scene controls

Move the activity, keep the world.

In-map activity scenes have their own placement list and sliders for X, Z, floor offset, rotation and scale. A firing range can sit off-center inside a district. Its geometry and collision move with the module; generating a new world preserves placed activity modules and independent inlays.

Object tuning

Fine adjustments stay available.

Placed items support position, elevation, rotation, scale, duplicate, remove, focus and existing undo controls. World alignment and the placed-object layer can also be adjusted separately. Editor visibility toggles aid composition; hiding a layer in the editor does not remove it from saved gameplay.

The current creation toolkit

Buildings & interiors

Twenty-five enterable building templates cover taverns, saloons, shops, banks, services and social venues. Furniture and interactive devices can be placed inside suitable interiors.

Drawing & depth

Custom item tools preserve vector strokes, colors, depth, bevel, material and configured behavior. Generated forms provide playable geometry; an extruded drawing is not automatically a rigged character.

Appearance & motion

Avatar Look Lab, compatible fitted pieces, material accents and available animation clips support customization. Each scene instance retains its own saved settings.

Gameplay authoring

Objects can be configured as decoration, seats, vehicles, conversations, quests, enemies, pickups, doors or supported devices. An object’s appearance alone does not create working gameplay.

06 · Gameplay and multiplayer

Shared rules on the server. Responsive presentation in the browser.

Shared room state

Simulation and authority

  • Player identity, room entry and supported movement commands
  • Collision, interaction distance, ownership and cooldown checks
  • Supported combat, pickups, seats, quests and vehicle actions
  • Machine controls, arcade turns and shared playback state
Client presentation

Controls and feedback

  • 3D rendering, cameras, animation and sound output
  • Keyboard/mouse, touch joysticks and on-screen actions
  • Movement smoothing and received-state interpolation
  • Compatible WebXR headset input and AR previews

RAD-TOX supplies a combat encounter loop in eligible environments; builder maps use their authored objects and activities. Room-level quest completion, health, scores and equipped or held state belong to gameplay data rather than an immutable avatar definition. Features can vary between hosted multiplayer, solo play and custom maps.

Placement geometry supports walkable floors, solid obstacles and gradual steps. Floor following, collision handling and reconciliation aim to keep walking consistent as shared state arrives. The project still needs repeatable performance measurements across physical phones, desktop GPUs and increasing room sizes before publishing frame-rate or capacity targets.

Progression scope: character classes and traits describe roles such as creator, builder, explorer, fighter, companion and merchant. A universal XP campaign, fully balanced competitive modes and identical progression across every custom game are development goals, not established platform-wide guarantees.

07 · How gameplay works

Explore, interact, complete a rule-driven activity and save the right result.

Movement and viewpoint

WASD/arrows or touch sticks move the player; drag or swipe changes the look direction. View / V switches first person and top down where supported, preserving the player and active match. The browser remembers this camera preference. Double-tapping clear ground can move directly to it. Vehicles, seated rides and WebXR use their appropriate camera and control modes.

Interaction and equipment

Approach a usable object and press E / Use, then follow its contextual actions. A seat, machine, fishing rod, vehicle or weapon has a specific function; visible appearance alone does not supply that function. Proximity, ownership, occupancy, action timing and map rules determine whether the server accepts an interaction.

Challenges and people

Quests expose discovery routes, ordered checkpoints and facility jobs. People & favors adds local conversations, introductions and return-to-contact tasks. Residents maintain bounded memories, needs, roles, skills and relationships; their local rules do not require an external language-model service. Their practice and demonstrations are resident activities, not automatic completion of player quests.

Input and recovery

Activity menus release conflicting held inputs; leaving a vehicle or changing maps releases its controls and abandons incompatible work. Travel can cancel active favors, races, fishing actions and delivery contracts. Saved progress survives according to its owning system; cancellation does not imply that an unfinished reward has been earned.

Three different gameplay layers coexist. Shared explorer rooms simulate movement, collision, object actions, residents and supported world activities. Dedicated sports services manage hockey and live park matches. Browser-local games handle their own presentation and solo rules, including the tropical resort and solo park attractions. The client supplies controls and rendering; an authoritative activity computes accepted scores, outcomes or rewards on its server. This separation explains why a local arcade best, a room quest score and a wallet MZK receipt have different persistence and value.

Creation is another playable loop. Choose a template, place or import supported assets, move and tune them, assign a supported behavior, then test or publish. Buildings, interaction profiles, quests, machine rules and attraction assemblies provide reusable functions. Custom cabinet templates select existing server games; they do not execute arbitrary creator code. Saved map copies preserve supported settings while retaining the account and ownership checks required for paid assets, publishing and private content.

Desktop, mobile and headset access share the activity. Touch actions expose the relevant controls without a keyboard. Compatible WebXR uses tracked head movement, controller rays and in-scene menus for supported sports, rides, fishing, factory tests and other activities. World introductions, requested conversations and new objectives can use the app's local neural voices; account audio settings control voice choice and mutes. Device permissions, browser support and actual headset testing still determine availability.

Persistence follows the record. Wallet balances, owned items, catches, production and eligible reward receipts belong to durable account records. Explorer room saves retain supported world state and personal room progress. Published maps retain scene configuration. Browser drafts, camera preferences and solo best scores remain local unless their flow explicitly saves them. Dedicated live park rounds are session state and should not be described as permanent match archives. No universal campaign or identical reward scheme spans all maps.

Watch, listen and speak

09 · Economy and rewards

Clear balances. Clear rewards. Clear ownership.

The platform uses several distinct accounting systems. MZK is recorded in the server’s user ledger; room score and arcade practice credits have their own purposes. Fishing sales, qualifying fitness sets and freight deliveries can create validated MZK rewards under their activity caps. The casino uses wallet MZK wagers, while arcade cabinet practice credits remain separate. External crypto payments must be verified before order delivery.

MZK balance

Used by supported purchases, land and configured game actions. Accepted coin collections can credit this balance through the server reward path.

Room score

Tracks supported activity and quest outcomes. The summer camp quest awards 35 room score; that result does not itself grant 35 MZK.

Arcade practice credits

Cabinet play balances for slots, poker and other supported games. Practice results do not imply a withdrawable prize or a wallet payment.

Other builder counters

Legacy Game Space flows may display Builder Coin or other counters. Their labels and quoted charges belong to that flow, not automatically to the MZK ledger.

These counts describe this revision's library, not unique owners, circulating tokens or units sold.

Current retail prices and resale prices

Retail prices are configured by catalog rules. The display conversion is 100 MZK per US dollar; it is a store denomination, not a cash redemption promise or a market exchange-rate feed. Basic items are free. Typical current rules price avatars at 300 MZK, vehicles at 750 MZK, creatures at 150 MZK and many land-model or building assets at 500 MZK. Materials have separate per-piece prices. Explicit factory, fitness and funhouse prices take precedence within their supported limits. The checkout quote establishes the actual charge.

Proposed valuation policy, for future adoption

Assess an asset's supported functions, compatibility across maps, build quality, reproducible replacement cost, verified provenance and completed sales. Any scarcity premium should require an enforced edition limit. Publish the asset version, entitlement, consumption rules and known restrictions beside its price. A future appraisal could show a reference retail price, production cost and recent comparable sales separately; the current app does not calculate an automatic fair value, scarcity multiplier or guaranteed return.

11 · Factory, minting, freight and market

Make a model, deliver the order, collect ownership, then use or list it.

The implemented factory loop creates an identifiable game item in the server's Backpack ledger. Calling this a game-item mint describes that creation receipt. It does not send an NFT transaction or establish an on-chain edition. The factory truck route, the Hormuz shipping game and physical merchandise fulfillment are separate workflows.

  1. FundChoose a recipe at procurement
  2. ProduceFabricate, assemble and test
  3. DispatchLoad and deliver in the same truck
  4. CollectCreate the Backpack item once
  5. Use or listFollow the destination and market rules

A complete production shift

At Procurement & jobs, fund an Aster Training Missile order for 180 MZK or an Orbit Cargo Rocket order for 320 MZK. The market labels the equivalent designs Atlas Training Missile and Atlas Cargo Rocket. Each account has one current order and must collect it before starting another. Required fabrication, assembly, calibration, loading and dispatch stations must exist before the server accepts payment.

Operate the three production cells in order from their marked approach pads. Missile cycles take 7, 9 and 6 seconds; cargo rocket cycles take 9, 12 and 8 seconds, plus walking and freight time. Meeting a crew member and enabling assistance reduces subsequent cycle duration by 25%. Machines have shared reservations. Moving, disabling or deleting equipment during a cycle requires repeating the affected cycle, without another kit charge.

After calibration, drive the factory dump truck to the loading bay and stop. Load the order, follow the haul lane, stop at dispatch and deliver using that same truck. The server checks the correct vehicle, station proximity, stopped speed and minimum elapsed haul time. Exit with free hands and collect at dispatch. Collection creates one item with a stable factory job identity and a creation receipt; retries return the existing result. Completed jobs add fabrication and logistics skills and badges at 1, 5 and 10 completions.

Orders, spending, machine leases and receipts persist in the user database across travel, reconnection and restart. Leaving the map does not refund an order; return to its originating map to finish. Client-edited metadata cannot create a valid factory receipt. The original crafter can deploy the completed model, or offer it through the eligible Backpack listing flow. Proving-ground tests follow verified resale history to the current owner. Generic factory display deployment still checks the original crafting wallet, so resale does not yet establish identical support in every placement path. Listing is a separate owner action, so dispatch does not automatically sell the item.

Testing adds gameplay progression

The neighboring Atlas Proving Grounds accepts receipt-verified crafted or purchased models. Configure a matching accuracy or cargo profile, reserve the shared pad, deploy, arm and launch a scripted test. Abstract alignment produces a score out of 100; 40 qualifies. Tests reuse the item, charge no additional MZK and award no MZK. Qualifying in both official profiles unlocks the Mountain Nuclear Research Compound, whose three-color containment puzzle opens the deeper bunker. Custom facilities remain sandbox activities and do not grant official clearance.

Maritime freight turns deliveries into useful inventory

The 2.8 km Strait of Hormuz Shipping Academy connects six ports with eight contracts. Board the free feeder, accept a manifest, alternate loads to balance the vessel, secure cargo and follow the ordered checkpoints. Dock slowly at the correct berth and unload every container. Cargo mass affects handling; hazards and hull damage affect quality. The larger container ship unlocks after two deliveries and the tanker after five; owning the corresponding market vessel also supplies access.

Base contract rewards range from 20 to 70 MZK before quality adjustment. Destination shortages can add up to 15 MZK, fixed when the manifest is accepted; induction retains its starter reward. Three AI shipping companies work their own cranes, voyages and warehouses. Freight League runs last 20 minutes after 15 seconds of preparation. Completed deliveries score from published route distance, cargo units and quality; prizes are 90/55/30 MZK or 15 MZK for a lower-ranked participant with a scored delivery. Delivery and league rewards share a 400 MZK daily account cap.

Delivered provisions exchange for a Medkit unlock or ten prepaid wood pieces; machine parts exchange for five metal pieces; tool stock unlocks a Scanner or professional fishing rod. Stock remains a dock-exchange resource. These rewards connect shipping with Tools and Builder, while normal ownership and market rules apply to the resulting items.

Boundary of the current factory-to-market connection

Factory dispatch currently ends in Backpack. Maritime manifests carry configured shipping cargo; they do not load a crafted rocket instance, require its ocean shipment before resale or automatically publish it to market. A unified factory → warehouse → ship → buyer pipeline would need linked item custody, cargo manifests, delivery receipts and sale settlement. That is a proposed extension, not a completed feature.

Current account model

Server-backed ownership

Inventory and linked wallet identity are durable application records. Ethereum sign-in uses a challenge and signature; an address alone is not proof of control. A connected wallet does not make all inventory an on-chain asset.

Portable gameplay files

Share references, retain ownership checks.

14 · Persistence, recovery and trust

Keep the world’s records separate from its presentation.

Persistent services

The Node service manages accounts, inventories, purchases, maps and shared-room records, including factory jobs, catches, freight stock and eligible settlement receipts. Activity rewards and custody are checked against their protected records rather than trusting editable client memory. Production persistence depends on configured durable storage for the data and upload directories. Static hosting alone does not supply these services.

Admin master state

Authenticated administrator tools can compile member and land data and export a master state file. Validation and controlled restore can replace server records and included local uploads, with an automatic recovery copy before replacement.

Recovery boundaries

Master files include captured server data and local assets, not deployment secrets, server code or externally hosted files. Blockchain payments are history and are never replayed. Browser-only drafts and unsaved tournaments are outside that capture.

Current protections

Authentication, permission checks, request validation, selected rate limits, private-asset controls, origin checks and HTTP security headers protect supported operations. These measures do not constitute independent certification or a blanket search-engine safety endorsement.

Operational status: backup and master-state functionality exist in the code. Offsite retention, restore drills, production monitoring and load capacity must be operated and measured for the actual deployment; this review does not certify those operational practices.
